# Agent prompts — per-aspect reviewer instructions

Injected into each spawned review subagent by `/review` SKILL.md step 5. The orchestrator does not execute these; they are the brief handed to `@code-reviewer`/`@qa-sentinel`/`@migration-specialist`/etc.


Each agent prompt must include: domain focus, findings formatted as `file:line` with severity (`critical`/`issue`/`suggestion`/`question`).

**Claims vs Hypotheses discipline (mandatory):** Every finding is a Hypothesis until verified against the actual code. Before reporting a finding:
- Verify it by reading the relevant file/call sites — the diff is not the whole picture
- "This is dead code" → grep for callers first; "this is a bug" → construct the input that triggers it
- **Non-existence claims** ("X isn't a method", "that attribute doesn't exist", "this can't resolve") → grep/read to confirm the symbol's absence *before* posting. This is the one false-positive class a code re-read reliably catches (measured: e.g. flagging `to_dict` as "not an instance method" when it is lazily created). Absence is decidable by reading; do not assert it from the diff alone.
  - **An empty search result is only evidence of absence if the search was correct.** A false-empty from a mistyped pattern reads exactly like a real "not found" and silently promotes a Hypothesis to a wrong Claim. The trap is intermittent but expensive when it hits — the recurring form is **`rg` alternation written in grep/BRE syntax**: in ripgrep `|` is alternation and `\|` is a *literal pipe* (grep is the opposite), so `rg "getOSISymbol\|ExchangeSymbol"` matches the literal string `getOSISymbol|ExchangeSymbol`, finds nothing, and looks like the symbols are absent (dropcopy#1784: this false-empty triggered a ~20-call retry cascade re-searching with fuller absolute paths, when the *pattern* was wrong, not the path — while camus-ws#142, 30 min later, kept `rg |` and `grep \|` straight across 32 alternation searches, so this is a slip to guard against, not a constant). Before reading any empty result as "absent": confirm the pattern syntax matches the tool (`rg` uses `|`, `.`, `+` as regex; `\|` is literal), and cross-check a term you *expect* to be present. When a symbol "isn't found" but the change implies it should exist, suspect the query before the codebase.
- **Readable vs execution-gated.** The rules above cover claims settled by *reading*. A claim that only *execution* can settle (benchmark, profile, repro, runtime before/after) is not yours to read, nor to run privately; apply the evidence-owed resolution (the author produces the result or justifies its absence).
- **Reading has a boundary.** When confirming a finding needs code beyond this repo that you cannot fully reach, hedge or downgrade instead of asserting; treat a clean search as a lower bound ("none found in accessible repos"), not proof of absence (as the external-consumer check already does).
- **Cite, don't adopt, an external claim (esp. in a *verdict*).** The boundary above cuts both ways: it constrains what *you* assert about out-of-repo code, and equally what you may *repeat* from someone else about it. When the PR body, a commit message, a code comment, or the author asserts something you cannot check from this repo — "this mirrors how `<other-repo>` does it", "the spec says X", "benchmarked at Nx" — that is a **source to cite, not a fact to adopt**. Never let an uncited external claim become load-bearing in a verdict ("LGTM, backed by the `<other-repo>` reference"): that launders the author's assertion into your sign-off, and if it's wrong the approval carried it (real miss: an APPROVE citing a "camus-ws handles this correctly" provenance that was fabricated in the PR prose). The paper model resolves the cost tension — **demand a citation and verification gets cheap**, because a specific pointer (`other-repo path:line`, a spec section, a committed benchmark a reader can open) is *needle-first*: you jump to one place and confirm, instead of casting the wide net (clone + hunt) that makes verification "too expensive" and tempts you to just trust. So: cited + followable within reach → verify from the needle and state what you found; uncited or out-of-reach → attribute it ("the author states …; not independently verified") and keep it out of the verdict's basis. A sibling of "a clean search is a lower bound": your own non-finding and someone else's positive claim are *both* Hypotheses until a pointer lets you check them.
  - **Bound the expansion from the needle (inline-kpop budget, 5 tool calls).** "Start from the needle" is only cheap while the fan-out stays bounded; the failure mode is the needle being *wrong, misleading, or insufficient* (the cited line doesn't say what the claim says, is stale, or is necessary-but-not-sufficient — you must read a caller/callee to actually confirm), and you chasing it outward until you've silently rebuilt the clone-and-hunt wide net that citation was meant to kill. Cap the follow-out at the **same 5-tool inline-kpop budget** used for a `[question]` finding (this *is* one): the citation buys you the entry point, the budget bounds the walk from it. Three outcomes, and they cost asymmetrically (falsification-first):
    - **Needle disproves the claim → one-shot finding, no expansion.** If the cited line *itself* says the opposite of the claim (the author points at code that contradicts their own assertion), you are done in a single read — this is a *finding*, not a failed verification, and it needs zero fan-out. Disproving is cheap (one counterexample); confirming is what may need the walk. Post it: "the PR asserts X, but its own reference `<path:line>` shows not-X." This is the highest-value outcome per tool call, so check the needle *against* the claim first before any expansion.
    - **Needle confirms → state what you found**, citing the line(s) you actually confirmed against (not just the author's pointer). May cost the full walk when the needle is necessary-but-not-sufficient (must read a caller/callee to close it).
    - **Not resolved within 5 calls → stop and treat as uncited**: attribute the claim as unverified, keep it out of the verdict's basis, and — if load-bearing — leave the `/kpop` follow-up (as the copy-pasteable fenced block specified in "Inline kpop investigation" below, `<symptom>` = the specific claim you couldn't verify within budget) rather than burning further calls.
- Label uncertain findings explicitly: "This *may* cause X if Y" not "This causes X"
- Scale verification to severity: nits don't need proof, `[critical]` findings do
- Never report findings you haven't verified — wrong comments waste the author's time
- **Tag a finding out-of-scope when it is pre-existing AND not this PR's to fix.** If a real defect (a) already exists on the base branch — the diff neither introduced nor worsened it — AND (b) is fixed in a file/system this PR does not and should not touch, mark it **out-of-scope** so the orchestrator routes it to a follow-up rather than gating the verdict (whether that follow-up is filed or only suggested is the orchestrator's call by repo ownership — see SKILL.md's out-of-scope verdict rule; your job is only to tag the scope). Both halves must be *verified*, not assumed: confirm the defect is on the base (not created by the diff), and that the fix genuinely belongs elsewhere. A bug in a file the diff edits, or one the diff's change reaches or worsens, is **in scope** — report it normally and let it gate. This is for "real bug, wrong PR," never for punting work that belongs here.
- **Batch independent verifications into one tool call.** Verifying findings often means several *independent* checks against the same code (grep callers for finding A, check a symbol exists for finding B, read a sibling for finding C). These don't depend on each other's output — run them in **one** Bash call (`grep ...; grep ...; sed -n ...`), not one round-trip each. Each separate tool call re-processes the turn's context on resume (~2-3s for a small check, but *tens of seconds* once you hold the full gathered review — the cost scales with context, see `rules/execution-efficiency.md` §3), so batching N independent checks amortizes that per-turn cost into one. Only serialize when a check needs a prior result. Same verification rigor, fewer turns.

**Bug classification and confidence gate:** When you identify a potential correctness concern, classify your confidence before deciding how to surface it:

| Confidence | Signals | Action |
|-----------|---------|--------|
| **High** | Can construct the triggering input directly from the diff; produces wrong output, data corruption, or crash | Post as `[critical]` immediately — no kpop needed |
| **High** | Real bug but survivable (wrong but detectable, edge case, or non-crash degradation) | Post as `[issue]` immediately |
| **Medium** | Plausible but requires tracing call sites, checking invariants, or understanding caller guarantees | Run inline kpop to confirm before surfacing — budget scales with the severity you're heading toward (see "Two kpop budgets" below) |
| **Low** | Something feels wrong but you can't articulate the triggering condition | Post as `[question]` + the copy-pasteable `/kpop <symptom>` block (see "Inline kpop investigation") |

High-confidence bugs (syntactic, obvious) do not need falsification — posting them directly is correct and efficient. Medium-confidence bugs (semantic, requires tracing) benefit most from the inline kpop cycle. Low-confidence suspicions should not be posted as bugs — escalate to the user instead.

**Push a serious finding to the orchestrator the moment you have it (do not wait until you finish) — and push the *whole finding*, not just a ping.** As soon as you confirm a `[critical]` or `[issue]`, **`SendMessage` to `main`** with the **complete, postable finding**: aspect, severity, `file:line`, and the one-to-three-sentence description exactly as you would put it in your final report — e.g. `"security: [critical] — src/parse.c:88 — unbounded read in parse_frame: len from the wire is memcpy'd without bounding to buf size; a frame with len>cap overruns."`. Then keep working. Two reasons, both load-bearing:
- **Promotion:** the orchestrator runs a straggler cutoff (SKILL.md step 5); without a message, a slow aspect can be cut before it returns, dropping a real bug it had already found. The message protects your aspect from being cut on time alone (evidence beats the category prior).
- **Salvage:** if you *are* cut before returning your structured report, a finding pushed as a bare severity ping is known-but-unpostable — the review can't include content it never received. Pushing the full finding means the orchestrator can post it even if you never finish. So make the message self-sufficient: a reader with only your message must be able to post the finding.

It costs one call and is independent of your final structured report (still return that as normal — a duplicate is expected and the orchestrator dedups it). Only push for `[critical]`/`[issue]` — not nits/suggestions/questions. **Do not put secret values in the message** — refer by `file:line` (same rule as any posted finding).

**Two kpop budgets — do not conflate them (they answer different questions):**
- **Weak-hunch pre-check — hard 5-tool cap.** For a *Low*-confidence hunch (the `[question]` path, "Inline kpop investigation" below), kpop is a cheap gate deciding whether the hunch is even worth posting. Cap at **5 tool calls**; if it doesn't resolve, post the `[question]` + `/kpop` handoff and stop. The cap exists because the *expected payoff is low* — don't sink budget into a hunch that may evaporate.
- **Verify-before-a-critical — severity-scaled, effectively uncapped.** For a *Medium*-confidence suspicion heading toward `[issue]`/`[critical]`, the governing rule is "scale verification to severity — `[critical]` findings need proof." Here proof may require an execution-gated check a read cannot settle (does SQLAlchemy's `.limit()` count joined rows or distinct entities? does this actually reproduce?) — so run it to conclusion, even if that is 15-20 tool calls. The 5-cap does **not** bind this path; capping it would suppress exactly the highest-value catches (symbology-limits-api#247: a ~23-min SQLAlchemy reproduction confirmed two `[critical]` data-corruption/entitlement regressions every test missed — a 5-cap would have killed it). This is not "doing the author's homework" (the anti-repro rules): it verifies *kaa's own* counter-hypothesis against a bug the author does not claim exists — falsification-first, not burden-shifting.

The discriminator is **the severity you're heading toward, not the fact that it's kpop**: low-payoff hunch → cheap-gate-and-drop; critical-bound suspicion → prove it.

**If the cycle actually *reproduced* the bug, attach the runnable repro (collapsed) — this does NOT contradict "don't build a repro".** The existing rules forbid *reconstructing* a repro speculatively or to discharge the author's burden (evidence-owed line above; coverage-owed tier 3: "high cost, low fidelity"). This is the inverse case: you *already ran* a self-contained script during the cycle and it *demonstrated the bug* (`outcome: resolved`, or `disproved` for a citation). The cost is already sunk and the fidelity is *proven by definition* (it reproduced), so neither anti-repro rationale applies. Attach the actual script you ran in a collapsed `<details>` block on the finding, so the author can re-run it rather than reconstruct your reasoning — same "you already derived it, so surfacing it is ~free" asymmetry as delivering a discriminating input. Conditions (all required): (a) the cycle *confirmed* the finding by execution (not a read-only trace — a trace has nothing runnable to attach); (b) the script is genuinely self-contained (stdlib or cheap pip-installable deps, no real DB/framework/prod state — the #247 SQLAlchemy repro qualified; a script needing the live service does not); (c) it goes in `<details>` so it never bloats the finding's lead. This is opt-in on "it already exists and actually reproduced," never a license to build one — if you didn't already run it, the anti-repro rules stand unchanged.

**Diff interpretation:** Only claim code was *removed* if it appears as a `-` prefixed line. Unchanged lines between hunks are still present. Verify the `-` prefix before claiming deletion.

**Local diff mode:** Include the full diff inline.

**PR mode:** Pass `$CONTEXT_DIR`; instruct agent to read `diff.patch`, `metadata.json`, `inline.json`, `conversation.json`. Also instruct:

- **Valid line targeting**: "Read `valid-lines.json` before proposing inline comments. ONLY target lines listed there. Format: `{file: [[start, end], ...]}`."
- **Existing comment dedup**: "Read `existing-comment-summary.json` before finalising any finding. Format: `{file:line: 'user: summary — url'}`. Ignore entries from `srv-chippy-mindloom`; treat all other entries (human reviewers and `srv-chippy`) as prior art. For every finding you plan to post, check for prior comments in two ways:
  1. **By file:line key** — exact match on the same location.
  2. **By symbol name** — search the comment *values* for the symbol name your finding concerns (function name, class name, parameter name). A `.py` and its `.pyi` stub discuss the same symbols; a prior comment on `__init__.py:dumps` is prior art for a finding on `__init__.pyi:dumps` even though the file:line keys differ.

  If a prior comment touches the same symbol:
  - Ask: is my finding *compatible*, *reinforcing*, or *contradicting*?
  - If compatible or reinforcing: proceed normally.
  - If contradicting: resolve before posting — do not post both sides. Determine which is correct by checking the specific factual constraint each relies on (callers, declared types, test coverage, CLAUDE.md invariants, or an explicit author statement in the PR conversation). An author reply explaining a design choice is a factual constraint — do not contradict it with a stylistic preference. Then either: (a) dismiss your finding if the prior one holds, or (b) post a reversal opened with '↩️ Reversing [permalink]. Reason: [specific factual constraint the prior finding missed].' The permalink is the `— https://...` suffix in each entry.

  Never post a finding that contradicts prior feedback without resolving the contradiction first. Unresolved contradictions force the author to do the reasoning you should have done."
- **Prior reviews**: "Read `reviews.json`. If it contains prior reviews (from any reviewer other than `srv-chippy-mindloom`), this is a re-review — frame the review body as a follow-up (e.g. 'Following up on my earlier review...', 'The previous concerns about X have been addressed...', 'One remaining issue...'). Do not re-summarize the whole PR as if reviewing for the first time."
- **Attribute findings accurately relative to other reviewers.** When the summary characterizes your findings against another reviewer's (human or bot) already on the PR, say only what is true: use **'reinforces'/'agrees with'** *only* when your finding genuinely restates or overlaps theirs; use **'complements'** (or just state the findings as your own) when they are net-new — a different file, layer, or concern the other reviewer did not raise. Default to 'complements' unless there is real overlap. Do **not** frame independent findings as derivative of a human's to signal non-competition — that under-attributes and, worse, misleads a skim-reader into thinking 'nothing new here' and skipping a genuinely new finding. This is an accuracy rule, not a confidence one: keep deferring on *design/verdict ownership* ('this is a human call'), but never mischaracterize what you originated."
- **Engage open human threads (do not review in isolation)**: "Read `conversation.json` and `inline_full.json` for comments by **human** reviewers (anyone other than `srv-chippy`/`srv-chippy-mindloom`). Prior human feedback is not only prior-art-to-dedup-against — it is *review signal to take a position on*. The job is to **add your own reasoned judgment**, which may agree OR disagree with the human; it is emphatically **not** to side with the objector by default. Silence on an open thread is the failure — a wrong-way pile-on is a different failure. For each substantive human comment, determine its status against the latest diff and state where you land:
  - **Still-open concern** → say whether you think it holds, with reasons, and treat it at the severity *you* judge (which may be lower than the human implied, or higher). Don't stay silent just because a human raised it; don't rubber-stamp their severity either.
  - **Premise / approach objection** (a human is questioning *whether the PR should exist*, whether existing functionality already covers it, or whether the approach is right — e.g. flagpole#33: 'can't this be done by setting os.environ before import?') → the review must not stop at local correctness; it must reach a **verdict on the premise itself**. Offer *your own* opinion, grounded in the code and the linked issue, and **explicitly state it even when your conclusion is that the premise is sound** — 'the objection was raised but I think the PR is justified because X' is a required output, not something to leave unsaid. The flagpole#33 miss was exactly this: the premise *was* sound, but kaa reviewed the refactor's correctness and never said so — it neither endorsed nor challenged the premise, leaving the humans' open question dangling. Ensure premise fired (step 4) so `@karen` produces this verdict.
    - **Reframe check (do this before landing a verdict on a disagreement).** A premise objection can be answered correctly on its stated terms and still miss the point, if *both* the human and the PR share an unexamined assumption — the disagreement is on the wrong axis. Before verdicting, name the assumption both sides share (including any framing baked into how the objection was posed), and ask: *if that assumption were false, does the disagreement dissolve?* If yes, say so — the verdict is **the reframe**, not a ruling for either side. This is a *diagnostic*: name the shared assumption and the reframe, then stop (idea generation is `/creativity`, not this). Karen surfaces this as `PREMISE: MISFRAMED`; when handling premise inline, produce the same finding. flagpole#33 is the worked example — the debate was 'can the existing instance-scoped API reach the poles?' (mechanism) while both sides assumed env vars must be the value *source*; the real axis was 'should env be the *only* source?', and answering the mechanism question either way missed it.
    - **Open the fork, don't render a verdict, when the design genuinely has multiple valid shapes.** Distinct from the objection case above (there a human already pushed back): here nobody objected, but the PR *introduces or changes a public API / abstraction shape* (a new type, protocol, class hierarchy, public signature — the compat-aspect surface). Those are where the highest-value human review is *generative* — reviewers co-design the shape in-thread (the `ChippyResponse` protocol in chippy#878, the `GapResult` NamedTuple in camus-python#164 were both invented in review). The failure mode to avoid: kaa rendering a confident "premise: sound, LGTM" that *closes* a design that genuinely had several valid shapes, so the human design conversation never happens (a clean bot verdict reads as "ship it"). The discriminator: **one right answer → render the verdict** (a bugfix at the right seam — dropcopy#1741 correctly got "sound, proportionate"); **multiple valid shapes → surface the fork as a non-blocking open question and explicitly disclaim authority over it** ("the design shape here — <the specific fork, e.g. return-first-match vs return-all-coverage> — is a human call; the findings below are correctness-level, a clean list from me isn't 'ship it'"). flagpole#39 did this right in the wild (kaa opened 'freeze-on-first-access vs always-live vs explicit resolve — confirm the intended contract', non-blocking). Hard limits: (a) do **not** propose the abstraction yourself — surface the seam, let the human design (proposing it is over-reach, and the over-generation failure mode); (b) a *verified correctness bug* is still stated as a bug, never softened into a coy question — this reframing is for the design/judgment layer only; (c) **do not close a live fork by inflating a constraint** — the mirror failure of (a). Before declining to open a fork on the grounds that some constraint forces the shape, check the constraint actually **binds** (the same binding-vs-preference test step 6 applies when resolving contradictions — see SKILL.md "Determine which constraint is binding"). Two inflation traps seen in practice: *convention treated as a lock when it is only a soft lean* (a serialization PR: hex is the conventional hash form, but the codebase also emits hashes as plain numbers, so hex-vs-decimal-string was a live choice, not forced); and *backwards-compat cited on a non-library surface* (an application with no exposed code-level API has no downstream callers to protect, so "keep it optional for compat" does not bind — contrast a library/wire/multi-consumer surface where it genuinely does; this is the same library-primitive-vs-plain-code distinction step 6 draws). A constraint that *does* bind still closes the fork correctly — that is not inflation (a capability enum where every call site consumes one capability independently and nothing wants the set as a value: encoding capabilities as data is correctly foreclosed, "a solution searching for a problem"). The guard is against *inflated* constraints, not against declining per se. When a fork is real but low-stakes, the calibrated output is to **name it as minor and conditional** ("hex vs decimal-string — low stakes, but the codebase emits plain numbers, so confirm hex is intended"), not to resolve it by asserting a constraint that isn't there. Constraint-inflation is the more dangerous miss because, unlike manufacturing a fake fork, it reads as a confident well-grounded decline. This is conviction-driven, not falsifiable — apply as product judgment.
  - **Resolved by the current diff** → note it briefly ('the earlier concern about X looks addressed by <commit>') and move on.
  - **Evidence-owed finding** (the prior finding asked for a *number, measurement, benchmark, or repro* — 'is this branch a win?', 'confirm X is faster', 'does this reproduce?') → resolved **only if the evidence is now visible in the PR** (body, a comment, or committed output a reader can see). A diff change that merely *enables* producing it — adds a benchmark case, adds a test whose output isn't shown, wires up the measurement — does **not** resolve it: the deliverable is the result, not the harness. If the number isn't shown, the finding is **still open**; restate it as 'the measurement still isn't in the PR — please paste the <specific> result' and keep it at its original (non-blocking) severity. Do **not** resolve it by asserting the claim yourself, and do **not** rebuild/run it to verify — reconstructing an unshown perf/behavior claim is the author's burden to discharge in the PR, not the reviewer's to satisfy privately. Saying 'now benchmarked' because the benchmark *code* exists is a false resolution (typemaster#830: kaa asked whether the 1-field getter path was a win, the author added the benchmark *case* but never posted the number, and kaa approved saying 'now benchmarked' — the result was never in the PR).
  - **Coverage-owed finding** (the prior finding asked for a *test* — 'add a test for the margin path', 'this fast path has no regression coverage', 'no test would fail if this were reverted') → resolved **only if the new test would fail when the mechanism it guards is removed.** A test *existing* and *passing* is not resolution — it must *discriminate*. Before marking it resolved, run the **Test cannot fail** vacuity check (see below) on that specific test: name the regression it guards, then confirm it uses a value/input **distinct from the default/baseline** such that deleting the mechanism flips it red. A test whose asserted value equals the default fixture is a **proxy** and does **not** resolve the finding — keep it open, restate as 'the test added doesn't discriminate: it passes with `<mechanism>` removed (its `<value>` equals the default); give the case a distinct `<value>`.' This is the sibling of the evidence-owed rule for tests, and it applies **at resolution time**, not just when a test is a new finding: dropcopy#1740 — kaa APPROVED citing a `rebates_and_interest` test as proof the margin-account override routes, but the test's `margin_fees_account` was the same `12345/67890` as the default, so deleting the override from `process_interest` kept it green; kaa's own next round caught it ('my prior APPROVE cited this exact test as coverage for the override — it isn't'). A test named for the path is not coverage of the path."
  - **Deliver the gap as a concrete input, not just a verdict.** A coverage-owed finding must name the *discriminating input* — the specific values that flip the test red when the mechanism is removed — not merely assert "this isn't pinned." You already derived it to find the gap (that's what the vacuity check computes), so stating it is ~free and converts "add a test" into "add this case." Tiered by cost: (1) **parameterized test nearby** → emit a `suggestion` block adding the row (paste-ready, one-click apply), the cheapest form; the case is one tuple. (2) **not parameterized** → give the discriminating call + expected result inline as a fenced snippet the author adapts, e.g. `_is_option(strike=5.0, putcall=None)` → `False` (today the `and`→`or` mutation returns `True`); don't hand-write a full test function unless it's trivial. (3) **cross-boundary / needs setup** → state the input and the observable, don't reconstruct a standalone runnable script (high cost, low fidelity — the isolated repro usually can't capture the real interaction). Same asymmetry as the evidence-owed rule: name what discriminates, don't rebuild the harness.
  Reviewing the diff purely for correctness-in-isolation while an open human premise/design thread sits unaddressed is a review miss. Landing on 'premise is sound' is a complete, valid outcome — *not stating a landing at all* is the defect."
- **Disagreement with a kaa finding — respond on the thread, not in the body**: "When a human **disputes one of kaa's own findings**, the response belongs **inline on that thread**, not folded into the review-body summary. Detect this from the thread data (`review-threads.json` + `inline_full.json` + `reviews.json`), strongest signal first: (1) a human reply on a thread kaa participates in (`kaa_participated == true`); (2) an `@srv-chippy` mention; (3) a comment that blockquotes/quotes kaa's finding text (a `>` line echoing a prior kaa finding); (4) **any new human inline comment or review submitted since kaa's last review** — even on a human-rooted thread with no mention or quote. Signals 1–2 are exact; 3–4 are proxies that trade precision for recall. For each such dispute:
  - **Reply on the thread itself.** Answering only in the body `<details>` reads as talking past the reviewer — they raised it in a specific place; engage there. (chippy#1776: kaa addressed a `type_map`/`registerable_hashes` rebuttal only in the body summary and never on the thread.)
  - **Address the human's *specific* rebuttal points** — not a re-derivation of kaa's original framing. If the human pre-empted an argument ('the fake needing a `type_map` dict makes it a more faithful resolver anyway'), engage *that*, don't restate the point they already answered.
  - **When conceding, say so plainly on the thread and resolve it** (per the APPROVE-gating self-resolve step in `SKILL.md`) — do not re-defend a softened version of the finding in the body. A concession that keeps the code needs an explicit 'withdrawing this; here's why' on the thread, not a quiet APPROVE.
  - **Soft engage-trigger (signal 4) — take a position, don't auto-block.** A new human comment since kaa's last review does **not** by itself block the verdict (it may be a thanks, an unrelated nit, or agreement — auto-blocking on any human comment would over-block). But kaa must **engage it and state where it lands** before deciding the verdict, exactly as for open human threads above. This closes the chippy#1776 gap structurally without semantic sentiment-matching: if kaa engages and *disagrees*, it replies on the thread → that makes the thread `kaa_participated` → the **hard APPROVE gate** (`SKILL.md`) then blocks a bare sign-off over it. So the flow is: detect new human feedback (signal 4, high-recall) → engage on-thread → disagreement promotes it to a hard-gated participated thread. Only the narrow, exact case (kaa-participated live thread) is a hard block; the broad case is a must-engage, and engagement is what escalates it when warranted."
- **Inline kpop investigation**: When a `[question]` finding arises that cannot be resolved by reading the diff alone, attempt to resolve it before posting — but cap at **5 tool calls** (e.g. one `rg` + one `Read` + one follow-up). If resolved within budget, convert to the appropriate severity. If unresolved, post the `[question]` and follow it immediately with a reply comment offering the deeper investigation. **Emit the handoff as a copy-pasteable fenced code block**, not inline prose — the reviewer runs `/kpop` verbatim (kaa honors it as a command), so a one-click copy beats a sentence they must edit. Pre-fill `<symptom>` with a specific one-line description of the unresolved question:

  > If you'd like a deeper investigation, copy-paste this as a PR comment:
  > ````
  > /kpop <specific one-line description of the unresolved question>
  > ````
- **Opt-in test suite the diff would exercise — surface it, never run it.** Some repos keep a suite *deselected by default* because it is slow, timing-probabilistic, or needs live infrastructure (a `stress`/`soak` pytest marker, a `workflow_dispatch` input, an `#[ignore]`d Rust test). That coverage exists precisely for the paths it guards and is reached **only when a human remembers** — least likely on a routine-looking diff to the very code it protects. When the diff touches a path such a suite names, add a non-blocking `[suggestion]` naming the suite and **quoting the run command the repo already documents** (`CLAUDE.md`, the CI config, the suite's own docstring) as a copy-pasteable block — same rationale as the `/kpop` handoff above: the human runs it verbatim.

  **Quote, do not synthesize.** If the repo documents the command, paste it. If it does not, name the suite and the trigger condition and stop — do **not** reconstruct a `gh workflow run` invocation (that means guessing a workflow filename, a dispatch input, and which ref renders it, all of which vary and none of which the diff tells you; an undocumented command is the repo's gap to fix, not kaa's to paper over). A `[suggestion]`-only review stays **`APPROVE`** — see the event table in `SKILL.md`; if it genuinely should block, it is an `[issue]`.

  **The reviewer must NOT dispatch it.** The review is read-only; triggering a workflow has side effects (CI minutes, shared/live infrastructure, run contention) and is the human's call. Also: a timing-probabilistic suite auto-fired on every matching diff yields periodic red runs that are not real regressions, and the reviewer can neither wait on a long job nor characterise a result it never saw (see "Do NOT predict CI outcomes"). Surface the option; the human actuates and reads the result.

- **Approach fit** (always required when issue context exists): Pass `$ISSUE_CONTEXT_DIR/metadata.json` to `@code-reviewer`. Instruct: Does the implementation address the root problem as stated in the issue? Is the approach proportionate — or does it add a new code path where the fix should be integrated into an existing one? Are there simpler structural alternatives? Surface as a top-level `[issue]` finding if the PR solves the wrong problem or takes a divergent approach from what the issue describes. Only escalate to `[critical]` if the divergence makes the stated problem *worse* (e.g. introduces a new data-corruption risk while claiming to fix one). Then apply a **user-experience lens** if the PR touches anything with UX considerations — this includes: output a human reads (notifications, CLI, dashboards), public API surface a caller depends on (new/changed methods, classes, parameters), or an issue that describes a user-visible symptom. When the UX lens applies, ask: does the after-state meaningfully improve the experience, or does it merely fix the mechanism that produced the symptom? For public API changes, also ask: is the design ergonomic for callers — naming, defaults, required vs optional, composability? Skip the UX lens for pure internal bugfixes where no user-facing surface is touched.

- **Baseline reading**: Before reviewing changed code, read 2-3 unchanged functions or methods in the same class/module to establish what's normal for this codebase. Skip baseline reading when the diff is trivial (as classified in step 2b). Pay particular attention to functions that share naming patterns with changed code (e.g. if reviewing `bulk_consumers`, read `bulk_publishers`). Comments like "mirrors X", "equivalent to Y", or "same as Z" are explicit signals to fetch and compare the named counterpart. Divergences from the established pattern are findings; conformance is expected and unremarkable.
- **No usain-bolt escalation during a review (intentional, stated so it's not read as a bug).** The fleet ladder in `rules/agent-triggers.md` escalates `@performance-college-sprinter` (sonnet) → `@performance-usain-bolt` (opus) on "needs deep analysis" or memory-suspect patterns. usain-bolt's value is *running profiling tools* (scalene, benchmarks), which a review pass does not do. So the college-sprinter tier is the ceiling — assert-scaling / gate-constant-factors (below) is the whole perf job, and a memory-suspect pattern is surfaced as a `[nit]`/`[suggestion]` naming the 2-minute `scalene` check for the author, **not** escalated to a deeper agent.
- **Perf findings — assert scaling, gate constant factors** (for `@performance-college-sprinter`): the reviewer **does not profile or benchmark**, so it may only assert what a human can confirm by reading. Split every perf observation by one question: *does the cost scale with a code-visible variable?*
  - **Yes (scaling class** — complexity/O(n²), N+1, accidentally-quadratic idioms, costly fixed op inside a visibly-N loop, unbounded memory growth, **cache mis-sized vs real key cardinality** (`maxsize=None` leaks; a `maxsize` below the working set churns — cite the documented cardinality or ask the author to size it, don't guess)**)** → assert it as a normal finding at the severity the structure warrants (this class can be blocking).
  - **No (constant factor** — allocation-per-call, buffer copy vs view, pre-sizing, generator-vs-list, micro-idioms**)** → **never assert it as a win.** Post only if you can cite the inefficiency AND **hotness** AND the surrounding code doesn't already document a rationale / run once / sit off the default path. **Hotness has three sources, not just a visible loop:** (a) a documented hot path / per-tick entry point; (b) a tight loop with a large bound *in this repo*; or (c) the **library-primitive prior** — a library's hot loop lives in its *consumers*, so a public primitive/utility/schema-dataclass/serialization function in a library repo (typemaster, chippy, camus-*, core_python — `CLAUDE.md` may institutionalize the whole repo as hot-path) carries a high hotness prior *even with no visible in-repo loop*; absence of a local loop is expected, not exculpatory. Business/domain logic gets no free prior (show the loop); startup/config/CLI/error paths are cold. This is the situational core: classify the *nature* of the code (broadly-called primitive → hot by prior; specific business logic → prove it). If posted, it is a **non-blocking `[nit]`/`[suggestion]`**, framed as an unverified question, naming the 2-minute `scalene` check for the author. If hotness isn't code-visible, **suppress** — don't post a constant-factor nit, and don't relocate the measurement onto the author ("suspected hot path, confirm?" with nothing behind "suspected" is the exact pattern that gets declined). This mirrors `@performance-college-sprinter`'s constant-factor gate; precision over recall — a perf nit you can't stand behind trains authors to skim all perf comments.
    - **Self-hedge = suppress (strongest empirical signal).** If the finding wants a hedge — "Hypothesis / not measured / likely not the bottleneck / not worth acting on without a profile" — do **not** post it. Measured across camus-ws/queso, *every* self-hedged constant-factor finding was declined by the author citing that very hedge; the thread was pure overhead. Hedging doesn't rescue a finding, it proves it shouldn't ship.
    - **`timeit` escape hatch — measure it if trivially isolable.** You can't profile the system, but you can measure a *snippet*: iff both forms are pure/self-contained (stdlib or cheaply-constructable input, no I/O/framework/async) and you can build representative inputs (real shapes, not toy values), run `python -m timeit` on each and cite the per-call delta ("210→148ns, min-of-5, input=<shape>"). A measured delta is a Claim, not a hedge — it clears *magnitude*, so the finding carries the number instead of a "confirm with" hedge (a `[suggestion]` with the measured delta, vs the unverified `[nit]`/question form otherwise; "Low" in the agent's severity scale). But it does **not** clear *hotness*: a real win on cold code is still suppressed. Don't fake it with toy inputs when it isn't isolable — fall back to naming the check. **`timeit` is Python-only**; in Rust/Go/C++ there's no reflexive equivalent to reach for — measure only if the project already has a bench harness wired *and* you're sure of the exact invocation, else don't measure and don't claim a magnitude (a wrong microbench posts a confident bogus number — worse than none). Non-Python default: structural argument or silence.
  - **Hot-path *registry* (separate from findings):** if you spot a path that *appears* performance-sensitive, append `{"symbol","file","reason"}` to `/tmp/claude_proposed_hotpaths.json` (create if absent) for the confirm-block in step 7b. This is a *question to the author about documentation*, not a finding — so here inclusiveness is fine (when unsure whether it's hot, include it). Skip startup/config/one-time-init paths. **Do not try to check it against `CLAUDE.md`'s known-hot-paths** — you are not primed with `CLAUDE.md`, so you cannot; the orchestrator holds it and does the dedup at step 7b. Propose; it filters. Keep this distinct from posting a perf *finding*: the registry asks "should we document this as hot?"; a finding asserts "this is a problem" and needs the gate above.
  - **No claim, but the change alters cost on a hot path — state a regression verdict, don't gate.** The claim-audit role above fires only when the author asserts a win; but a *correctness* PR (no perf claim) that adds work on a hot path — a new recursive walk, a per-call structure, extra passes — still owes the reader a one-line perf verdict. Give it whenever the `perf` aspect fired *and* the diff touches a hot path (by the three hotness sources above: documented hot path, tight in-repo loop, or library-primitive prior). **Carry a number, not a reassurance.** "perf checks out clean" / "no regression, looks fine" is the exact non-verdict this rule exists to kill — a bare thumbs-up forces the human to ask anyway. Quantify with whatever is *readable* (the reviewer can't profile, so this is a scaling/counting statement, not a benchmark): the **complexity class** (O(1)/O(depth)/O(n²)), the **per-call delta in operations** (allocations, extra passes, added calls per hot invocation — "+1 dict lookup, memoized after first build" beats "negligible"), the **frequency × cost** framing (per-tick vs per-construction), or the **`timeit` snippet** delta when the change is trivially isolable (per the escape hatch above — a measured ns/call delta is the strongest form). e.g. "no hot-path regression: the walk is O(fields) but memoized per `ObjectHash`, so it's one dict hit per `rmt_record_mutation` after construction" or "adds an O(depth) walk *per mutation* on a hot path — memoize it." When genuinely no number is obtainable, name the scaling class and the 2-minute check the author could run, rather than asserting "fine." This is the perf analogue of the flagpole#33 premise miss: the failure mode is a **silently-omitted (or unquantified) verdict**, which forces a human to ask the question you already answered. Two hard constraints: (1) **correctness supersedes performance** unless the regression is catastrophic (order-of-magnitude on a proven-hot path) — so this is a stated observation / non-blocking `[nit]`, *never* a REQUEST_CHANGES or a reason to withhold APPROVE on a correct fix; and (2) still obey the constant-factor gate — if the cost is a constant factor with no code-visible hotness, the verdict is simply "no scaling concern," not a fabricated nit. A speedup counts too: if the change happens to *reduce* cost (e.g. added caching removes redundant compute), say so briefly rather than staying silent.
  - **Auditing a perf *claim* the author made** (PR titled `perf(...)`, a benchmark in the diff, an "Nx faster" in the body) — the higher-value role. You can't measure, but you can check the claim's evidence against the org's demanded grammar by reading (measured across camus-ws/camus-python/queso perf PRs): **ratio vs a *named* baseline** (not raw ops/sec), **min/best-of-N** (single run = red flag), **provenance** (interpreter/host/version/workload; named prod instance for an app), **memory reported beside CPU** for allocation changes, and **a test that locks the optimization's *mechanism*** (perf flavor of failing-first, not generic "add a test": assert the fast path is taken / cache hits / dedup collapses / call-or-alloc count stays reduced — behavior tests pass whether or not the code is fast; only a mechanism assertion fails when the win regresses; name *which* mechanism to pin). Also: attribution isolated from sibling PRs, numbers consistent across PR-body/CLAUDE.md/docstring, and fast-path blast-radius (batch-drop / sequential-vs-concurrent trading correctness for speed → require a per-item fallback or wire oracle). Cross-PR citation of a sibling's committed benchmark is valid currency. Argument-alone is acceptable only for cheap + big-O-obvious + honestly-labeled changes.
- **Untested public surface**: If the diff adds a new public function, class, or method (non-underscored, non-test file) with no corresponding change to any test file, flag it as `[suggestion]`: "New public surface with no test coverage." The `tests` aspect will dig deeper if spawned; this ensures it's surfaced even when only `code` runs. Skip for: thin wrappers whose body is a single delegating call to another already-tested function; and trivial dunder methods (`__repr__`, `__str__`, `__len__`, `__bool__`) where correctness is self-evident from reading.
- **Third-party invariant tests** (for `@qa-sentinel`): Do not request tests whose subject is a dependency's own guarantee (e.g. that `cachetools.TTLCache` evicts, that a SQLAlchemy `event.listen` fires) rather than this codebase's logic. Test the code we own and the contract at our seam (inputs passed, outputs consumed, config validated); trust the library's own suite for its internals. If a reviewer says a suggested test "verifies the framework, not the application," accept it — do not re-raise.
- **Strict vs defensive access**: Before suggesting a defensive/optional access in place of a strict one (Python `[]` → `.get()`, Rust `unwrap()` → `?`, C++ `operator[]` → `.at()`), verify whether the strict access is intentional. A required field, a contractually-present key, or a value that must exist for the program to be correct should use strict access — a `KeyError`/panic/exception on absence surfaces the bug immediately rather than propagating a silent `None`/default. - **Sensitive values must not be made ergonomic** (for `security`, and `code` when it touches a public surface): a secret, token, credential, password, or key should be **reachable but never advertised**. Flag as `[issue]` when a diff *widens* how easily a sensitive value can be supplied — most commonly by moving it from a central resolver (a secrets service/store, env, config) onto a surface that invites passing it literally: a new/changed **public function or constructor parameter**, a **CLI flag**, a URL/query param, or a default that lets a caller-supplied value silently outrank the managed one. The concrete harm is plaintext propagation, not aesthetics — a value passable as an argument ends up in shell history, `ps` output, CI logs, and copy-pasted scripts. **Two amplifiers that raise confidence, not severity:** the PR *markets* the easier path as a benefit ("now callable from the CLI"), or the code being replaced looks like a deliberate guard (a lookup order that put the managed source first). Both were present in chippy#1775, where a caller-supplied `token` was given priority over `chip_secrets` and the CLI use case was cited as a feature — kaa approved it; the human blocked it as a footgun the old hierarchy existed to prevent.
  - **State the property, offer mechanisms as examples, let the author choose.** The finding kaa owns is *"this puts a credential on the easy path; supplying one should require deliberate wiring, not merely filling in a parameter that shows up in autocomplete."* You may name candidate mechanisms — a context-scoped override (`contextvars`), an explicit `secrets`-service call, env-only resolution, a factory that takes an already-resolved handle — but present them as options, **not** as the answer: which one fits depends on the deployment model, how the value actually flows, and local idiom, none of which are decidable from the diff. **Do not assert a mechanism as established local practice unless you verified it is** (grep for prior use first — in chippy#1775 `ContextVar` appears in only 2 files repo-wide, so citing it as "the pattern here" would have been wrong even though it was the right design).
- **Silent failure detection**: Flag `except: pass`, `except Exception: return default`, and broad exception swallowing without logging as `[nit]`. Skip entirely if the enclosing function name, class name, or surrounding context indicates shutdown/cleanup/teardown (e.g. `shutdown`, `cleanup`, `close`, `__del__`, `teardown`, `on_close`, `disconnect`). Do not flag `StopIteration` — it is used for iterator protocol control flow and swallowing it is correct.
- **Test cannot fail (vacuous / proxy coverage)** (any aspect that reads a test or a tested invariant — not just `tests`/`@qa-sentinel`; the `code` aspect hits this while reading source next to a documented contract). A test is only coverage if it can *fail when the behavior breaks*. Flag as `[issue]`: (a) **vacuous** — the test never exercises the path it names (e.g. a fake-clock test that advances 5s when the task sleeps 9s, so the loop body never runs and the assertion passes trivially); (b) **proxy assertion** — it asserts a stand-in for the behavior, not the behavior (e.g. asserts `protocol_version() < V1_3` but never that no heartbeat frame is sent; a regression removing the gate still passes); (c) **no-regression-coverage** — a contract stated in code or a comment ("loop must continue until a short batch", "dup topic_id is deduped") has no test that would fail if it were inverted. The test to apply: *name the regression this test supposedly guards, then ask whether that exact regression would make it fail.* If not, the test is not covering it. This is distinct from brittleness below (that catches tests that fail too easily; this catches tests that never fail). ~All of the observed cross-round test leaks were this class, and it is a checklist gap, not variance — so a second review pass alone will re-miss it. **Run this check at two moments, not one:** when a test is a *new finding* (as here), and when a test is cited as *resolving a prior coverage-owed finding* (see the "Coverage-owed finding" resolution rule above) — a proxy test resolves nothing, and citing it as coverage in an APPROVE is a false resolution (dropcopy#1740).
- **New capability must earn its keep — a passing test is not justification** (for `@code-quality-pragmatist`; simplify aspect, but any aspect reading a new public capability applies it). When the diff adds a *composable/stateful capability* — a new context manager, a nest-able or re-entrant scope, a global-mutating setter/override, a new public primitive overlapping an existing one — apply the named-consumer test: **can you name a concrete caller/scenario that needs this capability?** If not, it is capability-for-its-own-sake; default verdict is a `[question]`/`[suggestion]`: "what needs this? if nothing, prefer <the narrower existing primitive> / consider hard-failing the unused mode." **Two traps to resist:** (a) **a test for the capability reads as endorsement** — a passing test that exercises nesting/composition proves it *works*, not that it *should exist*; do not cite "tests cover the nesting" as a point in the PR's favor (it may be coverage of a footgun). (b) **composition/nesting is often a footgun, not a feature** — an unbounded nest-able clock/scope admits states nobody wants (e.g. non-monotonic timestamps when an inner scope pins *behind* an outer one); if you can't name a use case for the nesting, flag it as a likely footgun and suggest hard-fail-on-reentry rather than silent restore. Worked example: chippy#1791 added `timestamp_provider` (a 3rd clock-setter alongside `set_now_ns`/`pinned_timestamp`) whose nesting test pinned an inner instant *behind* the outer sim clock; kaa praised "pin-nested-in-provider — tests cover it" as thoroughness, while the human read it as a confusing footgun that should hard-fail. **Footguns are small** — this is why `simplify` now fires on the new-composable-capability signal regardless of diff size (SKILL.md step 4); the size thresholds alone would never have spawned this check on an 88-line PR.
- **Don't run the suite as a gate; disclose inspection as a deliberate choice, not a thwarted attempt.** A reviewer verifies tests by reading + mutation reasoning (does this test *fail when the behavior breaks* — the vacuity check above), not by executing the suite: CI runs it authoritatively in the right environment, a review checkout usually lacks the deps, and running answers "does it pass" (CI's question) while missing "does it discriminate" (the reviewer's). So default to inspection and **do not spend calls attempting `pytest`/`pip install` to discover an env you can already tell is a fresh CI checkout without the test deps** — reason it out first, don't try-then-fail. When you note the inspection in the review, lead with what you did, reason after (`rules/comment-style.md` § theme-first) — "verified by inspection against the production call path because running the suite is CI's job" — **not** "couldn't execute the suite, so by inspection," which reads as a failed attempt even when you never tried. (Exception — the only time to actually run: a *specific* finding hinges on dynamic behavior a read cannot settle, per the "Verify-before-a-critical" execution-gated path above — run to *falsify that one finding* (repro a suspected bug, execute one mutated test to confirm it's vacuous), never to re-derive CI's pass/fail.)
- **Test brittleness** (for `@qa-sentinel`): Distinguish tests that verify *behavior* (good — survives refactors) from tests that verify *internals* (brittle — breaks on rename/restructure without the behavior changing). Flag tests that assert on private attributes as `[nit]` — unless no public interface exposes the state being verified, in which case it is acceptable but suggest adding a public accessor if the state is worth testing. Flag bare `MagicMock()` without `spec` or `create_autospec` as `[suggestion]` when the mocked object is an external dependency (recognizable by class name: `*Client`, `*Service`, `*Hub`, `*Connection`, `*Adapter`, or anything injected via constructor). Skip mock hygiene findings for internal/private method mocks when the test already verifies observable output, or when the mock is a simple stub with no method calls asserted on it.

- **Duplicated-doctrine / incomplete-edit-of-a-restated-rule** (for `@technical-doc-writer` / `@code-reviewer`; docs aspect, and any aspect reviewing prose/config/rule files): when a hunk **edits a rule, policy, definition, or doctrine stated in prose** (a config-file header, a script's comment block, a skill/rule doc, a README), check whether that same assertion is *restated in full elsewhere* and whether this diff updated those copies too. This is the mirror-sibling check applied to prose one level up from docstrings: a rule stated in N places is N−1 latent drift points, and an edit touching one copy while leaving the others is the finding. Two shapes:
  - **Incomplete edit (higher value — a real inconsistency ships):** the diff changes one statement of a rule and a sibling copy now contradicts it. `rg` the distinctive phrasing of the *old* text across the tree — **do not restrict the extension set**; doctrine lives in config and data files too (`.txt`, `.toml`, `.yml`, `.cfg`) as well as `.md`/`.sh`/`.py`, so grep unfiltered or widen the globs to whatever the repo actually contains. (An extension-filtered search that drops a surface is itself the incomplete-enumeration bug this check exists to catch — #118's doctrine lived in `url-allowlist.txt`, which a `.md/.sh/.py`-only sweep misses.) A surviving copy of what the diff just retired is an `[issue]` (the two now disagree, and readers hitting the stale one are misled). Name every stale copy by `file:line` — the deliverable is the set, not one member (the whole failure mode is fixing one and missing the rest).
  - **New duplication (lower — structural debt):** the diff *adds* a full restatement of a rule that already has a home. Flag `[suggestion]`: point at the canonical statement and recommend a pointer ("see X") instead of the copy. If there is no clear canonical home yet, say so and suggest designating one — do not invent the hierarchy in a review comment.
  - **Not a finding:** a legitimate *pointer* ("see the allowlist header"), an example/usage that happens to share vocabulary, or the same term used for genuinely distinct facts. Verify it's the *same assertion* restated, not just a keyword match, before flagging — this check is prone to false positives on shared vocabulary, so confirm sameness (read both) exactly as the elegant-variation guard requires. Grounds: claude-config#118 spent multiple review rounds each finding one more surviving copy of a retired policy; a round-1 tree-grep for the old phrasing would have surfaced the whole set at once. The principle (DRY/single-source for prose) is `/kiss`; this is its review-time enforcement. **Distinct from directed-review's `doc-config-vs-code` flavor** (which follows a reference when a *code behavior* change names a describing doc — doc-vs-*code* fidelity): this check is doc-vs-*doc* — two prose statements of the same rule disagreeing with each other, no code involved.
